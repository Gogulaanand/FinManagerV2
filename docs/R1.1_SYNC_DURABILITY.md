## Decision

Use a typed server-side transactional batch as the upload transport, backed by a
local blocked-failure journal and explicit resolution actions.

The connector must submit one PowerSync CRUD transaction as one authenticated
server transaction. The server function must be `SECURITY INVOKER`, keep RLS in
force, allow only the known application tables and operation types, and apply all
operations atomically. A transaction is complete only when the server reports
`applied` or `already_applied`. A fatal, ambiguous, or unknown result leaves the
PowerSync transaction queued and writes or updates a local failure record before
the connector throws.

This deliberately combines the strongest parts of the plan's options:

- Option 2 supplies all-or-nothing server semantics and idempotent retry.
- Option 1 supplies a durable local record and an explicit user-controlled
  resolution path when the server rejects a write.

There is no direct per-operation PostgREST fallback. Falling back to that path
would reintroduce partial server application and would make a green connector
test insufficient evidence of transaction durability.

## Evidence from the current baseline

- `packages/sync/src/connector.ts` classifies SQLSTATE families `22xxx`,
  `23xxx`, and `42xxx` as fatal.
- `uploadData` sends each `transaction.crud` entry independently through
  PostgREST. If one entry fails after an earlier entry succeeded, the server can
  already contain a partial transaction.
- The fatal branch logs to the console and calls `transaction.complete()`.
  PowerSync's `complete()` removes the queued transaction, so the rejected
  operation has no durable recovery record today.
- `getNextCrudTransaction()` returns the complete local transaction and keeps it
  queued when the connector throws. That is the required blocked-queue behavior
  for the new fatal and ambiguous paths.
- Web and mobile providers currently call `disconnectAndClear()` whenever the
  session becomes null. R1.2 must change that behavior after this contract is
  implemented; this document does not change auth transitions.

## Upload contract

The connector will send a versioned request equivalent to:

```ts
type SyncUploadRequest = {
  protocolVersion: 1;
  clientInstanceId: string;
  transactionId: number | null;
  payloadHash: string;
  operations: readonly {
    clientId: number;
    table: string;
    rowId: string;
    op: 'PUT' | 'PATCH' | 'DELETE';
    data: Record<string, unknown> | null;
    previousValues: Record<string, unknown> | null;
  }[];
};
```

Rules:

1. `clientInstanceId` is an opaque random identifier generated for the local
   database. It is not a user id and is never derived from a password.
2. The server derives the owner from `auth.uid()`. A client-provided `user_id`
   is validated by RLS and cannot select another owner.
3. `table` is checked against an explicit allowlist. No client value is used as
   dynamic SQL without allowlist dispatch and identifier quoting.
4. `PUT`, `PATCH`, and `DELETE` retain the current PowerSync semantics. JSON
   columns are decoded before the typed table operation is applied.
5. The server writes an idempotency record in the same database transaction as
   the application writes. The key is the user, `clientInstanceId`, and
   `transactionId`; the payload hash must match on retry.
6. A retry after an ambiguous timeout returns `already_applied` when the
   idempotency record committed. If the transaction rolled back, the retry
   applies the complete batch again. No operation is treated as successfully
   uploaded from a client-side timeout alone.
7. A changed payload with an existing idempotency key is a protocol error and is
   recorded as an unknown failure; it must not be silently applied.

The server function must remain authenticated by the caller's Supabase JWT and
must not use the service-role key. RLS remains the tenancy boundary. The
idempotency table stores operation count, payload hash, and timestamps, not the
financial payload.

## Local failure journal

Add a `sync_failures` PowerSync local-only table. It is not part of the Supabase
sync rules and is preserved only when the app deliberately keeps local state for
recovery. Store one row per operation, with a shared transaction key, so the UI
can show a useful count while recovery can reconstruct the entire batch.

Required fields:

| Field                               | Purpose                                                         |
| ----------------------------------- | --------------------------------------------------------------- |
| `id`                                | Stable local failure-record id                                  |
| `user_id`                           | Scope queries and prevent cross-account display                 |
| `client_instance_id`                | Idempotency identity                                            |
| `transaction_id`                    | PowerSync transaction identity                                  |
| `client_operation_id`               | Individual PowerSync `clientId`                                 |
| `table_name`, `row_id`, `operation` | Operation identity                                              |
| `operation_data`                    | Local recovery/retry data; never sent to telemetry              |
| `previous_values`                   | Reversal/context data when PowerSync tracks it                  |
| `payload_hash`                      | Detect changed retry payloads                                   |
| `failure_class`, `error_code`       | Typed failure classification                                    |
| `safe_error_message`                | Redacted user-facing explanation                                |
| `first_failed_at`, `last_failed_at` | Failure chronology                                              |
| `retry_count`                       | Bounded retry/backoff accounting                                |
| `resolution_state`                  | `retryable`, `blocked`, `resolving`, `resolved`, or `discarded` |
| `resolved_at`, `resolution_reason`  | Explicit resolution audit                                       |

The failure journal is local recovery data, not an event-log destination. Logs
and Sentry receive only the failure class, table name, row id, operation id, and
payload hash. They never receive operation data, notes, merchants, account
balances, or raw PostgREST payloads.

All synced finance tables should enable PowerSync previous-value tracking where
the SDK supports it. This is needed for an explicit discard/reversal flow,
especially for updates and deletes. The implementation must verify the storage
cost and generated CRUD shape before enabling it globally.

## Failure classification and state machine

| Class           | Examples                                                     | Default behavior                                                   |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| `transient`     | network loss, timeout, 5xx, 429                              | Record attempt, keep queued, retry with bounded backoff            |
| `auth`          | expired token, missing session, 401                          | Refresh/reconnect once; then keep queued and require auth recovery |
| `validation`    | malformed date/type, 22xxx                                   | Record and block; user repairs or explicitly discards              |
| `authorization` | RLS denial, 42501, forbidden table                           | Record and block; never retry forever                              |
| `conflict`      | idempotency mismatch, unique conflict, concurrency rejection | Record and block with conflict details                             |
| `unknown`       | unmapped response, client/server protocol mismatch           | Record and block; preserve the queue for diagnosis                 |

State transitions:

```text
retryable -> retryable       (automatic retry)
retryable -> blocked         (bounded attempts exhausted or non-retryable error)
blocked    -> resolving      (user chooses retry, repair, or discard)
resolving  -> retryable      (retry requested; queue remains)
resolving  -> resolved       (server applied or already_applied)
resolving  -> discarded      (explicit user acknowledgement and queue completion)
```

The connector may call `transaction.complete()` only after a successful server
result or an explicit discard command. A rejected transaction is never completed
merely to unblock later queue entries.

## Partial-failure and recovery rules

- The server function is the atomicity boundary. If operation 2 fails, operation
  1 is rolled back and operation 3 is not applied.
- A response lost after commit is handled through the idempotency key, not by
  guessing whether individual operations landed.
- A rejected local transaction remains in the PowerSync queue. The failure
  journal is written before the connector throws; if journaling fails, the
  connector throws the journal error and never completes the queue transaction.
- Retry leaves the original queue transaction intact. Repair may update the
  local row, after which the original blocked transaction is retried or
  explicitly resolved according to the failure type.
- Discard requires an explicit user action, records the reason and timestamp,
  then completes the matching PowerSync transaction. It must not be an implicit
  side effect of sign-out, auth refresh, app restart, or queue cleanup.
- Export/recovery can include the local failure journal and affected local rows,
  but telemetry and ordinary logs remain payload-free.

## Required test matrix

The R1.1 implementation is not complete until these tests assert both the local
queue and the server-side result:

| Scenario                               | Expected assertion                                                   |
| -------------------------------------- | -------------------------------------------------------------------- |
| transient network failure then retry   | queue remains; retry succeeds; one server application                |
| RLS rejection                          | queue remains; authorization record is durable; no silent completion |
| check-constraint rejection             | queue remains; validation record contains table/id/class             |
| unique conflict                        | conflict record is durable; user action is required                  |
| first operation succeeds, second fails | server data is unchanged by the batch                                |
| ambiguous timeout after commit         | retry returns `already_applied`; no duplicate rows                   |
| ambiguous timeout before commit        | retry applies exactly once                                           |
| delete followed by update              | batch outcome is atomic and deterministic                            |
| auth token expiry during upload        | refresh/retry path is bounded; pending work survives                 |
| app termination during upload          | restart sees the queued transaction or a durable applied result      |
| journal write failure                  | connector throws and does not complete the PowerSync transaction     |
| explicit discard                       | completion occurs only after the recorded user action                |
| two users on one device                | failure rows are scoped and never shown across sessions              |

Use connector fakes for the unit matrix and a local Supabase/Postgres test for
the RPC atomicity/idempotency matrix. Do not claim a direct PostgREST mock proves
RLS, transaction rollback, or database idempotency.

## Implementation sequence

1. Add the decision and contract (this document and `DECISIONS.md`).
2. Add the Supabase migration for the idempotency ledger and typed batch RPC;
   add pgTAP tests for allowlisting, RLS, rollback, and idempotent replay.
3. Add the local-only failure table, typed failure records, redaction, and
   retry/discard repository methods in `packages/sync`.
4. Add `clientInstanceId` storage and previous-value tracking where required;
   verify both web and Expo/OP-SQLite schema initialization.
5. Replace the connector's direct per-operation upload with the typed batch
   call. Fail closed if the batch protocol is unavailable; do not restore the
   old partial-write fallback.
6. Add connector and repository tests for the matrix above, then run the
   focused sync tests before the repository gate.
7. Expose pending/failed-write counts and resolution methods to R1.2/R1.3.

R1.2 may then implement safe auth transitions and bounded final sync. R1.3 may
build the status surface only after these contract names and states are stable.

## Explicit non-goals for R1.1

- No sign-out/provider behavior change; that is R1.2.
- No sync health UI; that is R1.3.
- No full backup restore; that is R2.
- No general two-device conflict policy; that is R4, although idempotent batch
  replay is required here.
- No production release claim. Device, auth, and external observability gates
  remain separate evidence obligations.

## Exit criteria

- Every rejected write has a durable local record or is explicitly discarded by
  the user.
- No rejected transaction is completed by the connector.
- Multi-operation uploads are atomic at the server boundary.
- Ambiguous responses are safe to retry without duplicate application.
- Failure records and telemetry are redacted appropriately.
- The connector and database tests cover the full matrix and pass.

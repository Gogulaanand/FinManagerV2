# R2.4 Recovery Drill

Status: local isolated drill verified on 2026-08-02. Production and remote
Supabase operational evidence remain open.

This runbook exercises the R2.4 recovery contract without touching production.
The harness uses a sanitized, production-shaped fixture, temporary directories,
an isolated SQLite database, a simulated device-only key store, and a local
encrypted backup artifact. It never uses a real account, financial payload,
Supabase project, access token, or secret.

## Evidence boundary

The committed [sanitized drill report](evidence/r2.4-recovery-drill.json) is the
authoritative record for the local exercise. It contains per-scenario ISO
timestamps, measured durations, assertions, and evidence labels. The focused
tests are [r2-recovery-drill.test.mjs](../scripts/r2-recovery-drill.test.mjs),
and the executable harness is [r2-recovery-drill.mjs](../scripts/r2-recovery-drill.mjs).

This evidence proves the recovery control flow in disposable/local state. It
does not claim that the GitHub Actions backup workflow has produced a retained
artifact or that a managed Supabase project has been restored. The GitHub
Actions secrets page was checked in the authenticated browser on 2026-08-02;
`SUPABASE_DB_URL`, `SUPABASE_BACKUP_PASSPHRASE`, and
`DISPOSABLE_SUPABASE_DB_URL` were absent, so the backup and rehearsal workflows
were not dispatched.

## Preconditions and safety

1. Start from the repository checkout and verify the branch is the focused R2.4
   branch.
2. Use only the repository's sanitized fixture and temporary directories.
3. Do not set production URLs, real credentials, or real financial data in the
   local shell.
4. Do not point `DISPOSABLE_SUPABASE_DB_URL` at production. If the three
   repository secrets are later configured, the operator must verify the target
   project is disposable before dispatching the workflows.
5. Retain only aggregate reports and checksums. Remove decrypted dumps and
   temporary databases after each run.

## Local execution

Run the focused tests and the six-scenario drill sequentially:

```sh
pnpm test:recovery-drill
pnpm recovery:drill
```

The command exits nonzero on any failed assertion. The report records exact
steps and measured recovery time for:

| Scenario                        | Recovery exercised                                                                                                       | Local evidence           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| Accidental transaction deletion | Detect a missing transaction and restore it from the sanitized recovery artifact.                                        | Report scenario `R24-01` |
| Malformed migration             | Reject a broken SQLite migration without losing existing data, then apply a forward repair.                              | Report scenario `R24-02` |
| Lost mobile SecureStore key     | Fail closed when the device-only key is gone, create a new local database, and re-sync server-shaped fixture data.       | Report scenario `R24-03` |
| Corrupted local database        | Reject unreadable local state, replace it, and re-sync the fixture.                                                      | Report scenario `R24-04` |
| Compromised account session     | Revoke the simulated session, reject its reuse, re-authenticate a test account, and verify account ownership isolation.  | Report scenario `R24-05` |
| Full project loss               | Verify encrypted-backup checksums, restore into a fresh isolated project, and compare all required financial invariants. | Report scenario `R24-06` |

## Clean-account restore assertions

The R24-06 report must show equal source/target values for every item below:

- row counts for every fixture collection;
- referential relationships, including transaction account/category links,
  holding event/valuation holding links, and goal holding links;
- account balances;
- monthly debit and credit totals;
- XIRR cash-flow input count and values;
- goal target and current totals.

The restore is not considered successful if only table counts match. The report
also records checksum verification before decryption/restore and the measured
duration from simulated project loss through invariant comparison.

## Recovery procedures

### Accidental transaction deletion

1. Freeze further writes in the disposable fixture and record the incident start
   timestamp.
2. Confirm the transaction is absent and that the financial comparison differs.
3. Select the matching transaction from the versioned recovery artifact by its
   stable id.
4. Restore only that row in dependency-safe order and re-run the invariant
   comparison.
5. Record the restored id, end timestamp, and elapsed recovery time.

Production use of this procedure must use the product's restore/undo contract;
do not hand-edit production SQL rows.

### Malformed migration and forward repair

1. Clone the sanitized database into a temporary directory and capture the
   pre-migration row count/checksum.
2. Apply the deliberately malformed migration and require the database command
   to fail.
3. Verify the original row and schema are still present.
4. Apply a versioned forward repair migration, then verify the repaired schema,
   data, and migration marker.
5. Record both failure and repair timestamps and durations.

Never test a malformed migration against production. A production incident uses
the repository's forward-fix migration process and the backup policy's restore
path.

### Lost mobile SecureStore key

1. Stop the disposable mobile database and record the device-state timestamp.
2. Remove only the simulated device-only key; do not attempt to bypass the
   encryption boundary.
3. Confirm the old encrypted database cannot be opened.
4. Create a new key/database and re-sync the server-shaped fixture.
5. Compare the re-synced metrics and record elapsed recovery time.

The native contract is documented in [D-073](../DECISIONS.md): a lost key is
recovered by clearing app data or reinstalling and re-syncing, not by recovering
or synchronizing the key.

### Corrupted local database

1. Stop the disposable local database and record the corruption timestamp.
2. Detect the invalid database bytes/checksum and fail closed.
3. Preserve the corruption evidence label, discard only the disposable local
   copy, and create a clean local database.
4. Re-sync the fixture and compare the required metrics.
5. Record elapsed recovery time.

### Compromised account session

1. Mark the simulated session revoked and record the incident timestamp.
2. Require the revoked session to fail before any account data is returned.
3. Rotate the simulated test credential and create a new session for the same
   test account.
4. Verify the restored session sees only its own rows and that a second test
   account cannot read them.
5. Record the revocation, re-authentication, isolation assertion, and elapsed
   recovery time.

Production response additionally requires owner-controlled credential rotation,
session revocation, and review of Auth/security logs. Those actions are not
performed by this local drill.

### Full Supabase project loss

1. Freeze writes and record the incident start timestamp.
2. Create/select a new disposable project; never use the production project for
   a rehearsal.
3. Select a successful encrypted artifact and record its backup run id,
   retention, and artifact URL.
4. Decrypt only in the disposable runner, verify every checksum, and remove
   plaintext material after the restore.
5. Apply schema and data in one transaction with `ON_ERROR_STOP=1`; adapt
   managed roles separately as required by
   [SUPABASE_BACKUP_POLICY.md](SUPABASE_BACKUP_POLICY.md).
6. Run the clean-account comparison above and record source/target values,
   restore run id, rehearsal run id, end timestamp, and measured recovery time.
7. Reapply migrations/functions, then run the R2.2 restore and release checks
   before considering the replacement project usable.

The local R24-06 harness verifies steps 3–6 with a sanitized encrypted artifact
and a fresh isolated SQLite project. The GitHub Actions workflow remains the
authoritative GPG/Supabase implementation and requires the three absent secrets
before it can produce operational run evidence.

## Release interpretation

R2.4 local recovery evidence is complete when the report and focused tests pass,
all six scenarios have timestamps and durations, and the clean-project restore
matches every required invariant. R2.3 operational evidence remains **open**
until a real backup run id, retained encrypted artifact, checksum verification,
disposable-project restore output, and measured duration are saved. The personal
MVP release gate remains governed by
[PRODUCTION_READINESS.md](PRODUCTION_READINESS.md).
